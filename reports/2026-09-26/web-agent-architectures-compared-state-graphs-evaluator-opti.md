# Orchestrating Web Agents: A Decision Framework for State Graphs, Evaluator-Optimizer Loops, and DAG Orchestrators

## State Graphs: The Granular Control Plane for Dynamic Orchestration

State Graphs represent a low-level orchestration framework designed for building complex, stateful, and multi-step AI applications [[16]]. At its core, this architecture models an agent's workflow as a directed graph where nodes signify discrete units of work and edges define the transitions between them [[6,11]]. This approach provides developers with explicit, programmable control over the system's logic, enabling the creation of sophisticated agentic behaviors that go far beyond simple linear chains [[36]]. The most prominent implementation of this paradigm is LangGraph, an open-source framework from the creators of LangChain [[11,33]]. Unlike traditional workflow engines that treat steps as deterministic black boxes, LangGraph is specifically engineered to handle the non-determinism inherent in LLM-driven interactions, such as model hallucinations or rate limits [[14]]. Its fundamental design philosophy centers on managing state transitions explicitly, making it a powerful tool for orchestrating multi-agent systems where context and control flow are paramount [[34]].

The architecture is built upon three foundational components: Nodes, Edges, and State [[16,17]]. Nodes are atomic functions—typically Python functions—that perform a specific action, such as invoking an LLM, executing a tool, or running custom logic [[14,16]]. Each node receives the current shared state as input and can return updates to modify that state [[17]]. Edges are the connections that determine the next step in the execution path after a node completes its work [[16]]. They can be simple, direct links between two nodes (`add_edge`), or they can be conditional, using a routing function to decide the next node based on the content of the current state (`add_conditional_edges`) [[12,17]]. This conditional routing is a key feature, allowing the graph's structure to adapt dynamically at runtime, which is essential for handling branching logic and complex decision-making [[32]]. The third component, State, is a central data structure, often defined using a `TypedDict` or Pydantic model, that serves as the single source of truth for the entire workflow [[11,16]]. All nodes read from and write to this shared state object, which accumulates a complete history of messages, tool calls, intermediate results, and decisions throughout the execution lifecycle [[11]]. This persistent and centralized state management is what enables the graph to maintain memory across steps and facilitates robust fault tolerance [[36]].

A defining characteristic of State Graphs, particularly within LangGraph, is their native support for cycles [[11,33]]. Traditional Directed Acyclic Graphs (DAGs) prohibit cycles to guarantee termination, but many agentic processes, such as self-correction or iterative refinement, require looping back to a previous node [[8]]. LangGraph addresses this by allowing edges to loop back to earlier nodes, creating structures that can model ReAct (Reason+Act) loops, reflection cycles, or any other iterative process [[11,32]]. For example, a "researcher" node can generate an answer, a "validator" node can evaluate it, and if the evaluation is unsatisfactory, a conditional edge can route execution back to the researcher for a revision, all within the same graph instance [[14]]. To prevent infinite loops, safeguards must be implemented, such as tracking a revision count in the state and using conditional logic to terminate the cycle when a maximum number of iterations is reached [[3,51]]. This cyclical capability makes State Graphs exceptionally versatile for tasks requiring dynamic adaptation, error recovery, and continuous improvement, distinguishing them from more rigid orchestration models [[33]].

The fault tolerance and durability of State Graphs are primarily achieved through a mechanism called checkpointing [[6,11]]. After each node executes and updates the state, the entire state object is saved to an external storage backend, such as Postgres, Redis, or SQLite [[34,36]]. This creates a durable snapshot of the workflow's progress at every step [[12]]. If the application crashes or is interrupted, it can be resumed from the last successful checkpoint, rehydrating the state and continuing execution from the exact point of failure without having to restart the entire process from scratch [[33,36]]. This capability is critical for long-running, production-grade workflows where expensive LLM calls would otherwise need to be repeated [[8]]. Beyond basic fault tolerance, LangGraph provides explicit primitives for sophisticated error handling. These include `RetryPolicy`, which automatically retries a node's execution on transient errors like network issues with configurable exponential backoff, and `TimeoutPolicy`, which enforces hard time limits to prevent hanging nodes from blocking the entire workflow [[35]]. Furthermore, a dedicated `error_handler` node can be triggered after all retries have been exhausted, allowing for compensation logic, such as rolling back side effects or escalating the error for human review [[35]]. This combination of persistent state and granular fault-handling primitives makes LangGraph a robust choice for building reliable agentic systems [[14]].

In the context of multi-agent web systems, State Graphs provide a powerful abstraction for modeling complex interactions with the web environment. Individual browser actions—such as navigating to a URL, clicking an element, filling out a form, or waiting for content to load—can be encapsulated as distinct nodes [[43]]. The state object can track the current page URL, parsed DOM elements, extracted data, and conversation history with the user [[31]]. Conditional edges can then route the workflow based on the outcome of a page load or the result of a search query, while cycles can be used to implement retry logic for failed actions or to handle interactive elements like dropdown menus [[12,43]]. Parallel execution is also a natural fit for this architecture; a "fan-out" pattern can be used to spawn multiple nodes concurrently to scrape different sections of a website or query multiple data sources simultaneously, with a final "fan-in" node aggregating the results [[11,12]]. This ability to explicitly define and manage parallelism is a significant advantage over linear chains, which artificially serialize all tasks and waste wall-clock time [[15]]. Production examples demonstrate the effectiveness of this approach. Exa's deep research agent uses LangGraph to orchestrate hundreds of queries daily, dynamically adjusting the number of parallel tasks based on query complexity and intelligently deciding whether to analyze full page content or just snippets to optimize performance and cost [[31]]. Similarly, Klarna's customer service assistant, which handles millions of conversations monthly, leverages LangGraph to manage a multi-agent workflow that drastically reduced resolution times and improved customer satisfaction [[50]]. These cases highlight how the fine-grained control, fault tolerance, and dynamic adaptability offered by State Graphs make them a premier choice for building sophisticated and reliable web agents.

## Evaluator-Optimizer Loops: An Iterative Strategy for Quality Assurance and Self-Correction

The Evaluator-Optimizer Loop is an architectural pattern focused on improving the quality and correctness of an LLM's output through a structured, iterative feedback mechanism [[1,9]]. It operates on a fundamental principle of decoupling generation from validation, creating a closed-loop system where a solution is continuously refined until it meets predefined criteria [[2,10]]. This pattern is not typically a standalone orchestration framework but rather a higher-level control flow strategy that can be implemented within a broader system, including a State Graph [[51]]. Its primary purpose is to address the inherent unreliability of single-pass LLM generation by systematically identifying and correcting errors before a final output is accepted [[3]]. The core components of this architecture are a Generator (or Optimizer), which produces an initial response, and an Evaluator (or Critic), which assesses the response against a set of clear and measurable criteria [[1,2]]. The evaluation result, often a score or structured feedback, is then fed back into the generator to guide its next attempt, repeating the cycle until a satisfactory outcome is achieved or a stopping condition is met [[9]].

The operational mechanics of the loop involve a simple yet powerful cycle of `Generate -> Evaluate -> Refine` [[3]]. In the first phase, the Generator agent takes a task and initial instructions to produce a draft solution [[1]]. This could be a piece of code, a written report, a database query, or any other artifact. In the second phase, the separate Evaluator agent reviews this draft. The Evaluator's role is to act as a rigorous critic, checking the output for correctness, completeness, adherence to style guidelines, logical consistency, and other relevant metrics [[3,9]]. The feedback provided by the Evaluator is crucial; it should be actionable and specific, pointing out exactly what needs improvement rather than providing a simple pass/fail verdict [[42]]. For instance, instead of saying "this code is wrong," a good critique would specify that the function fails a particular test case or has poor time complexity [[1]]. In the final phase, the Generator uses this feedback to revise its output in a subsequent iteration [[3]]. This process continues within a `while` loop until one of several termination conditions is met. These conditions typically include achieving a minimum quality score, meeting a predefined success criterion, reaching a maximum number of iterations, or detecting convergence (where further revisions yield negligible improvement) [[1,3,51]].

This iterative refinement process offers several key benefits, most notably a significant improvement in output quality at the expense of increased computational cost [[2]]. By systematically addressing flaws identified by an independent evaluator, the system can produce more accurate, reliable, and higher-quality results than a single-generation approach [[9]]. This pattern builds a form of built-in quality control directly into the workflow [[9]]. Research has shown that such reflection-based methods can improve pass rates on coding benchmarks by 10-20 percentage points over baseline approaches [[3]]. The Reflexion framework formalizes this concept by having an agent generate a verbal analysis of its own mistakes, storing these reflections in a memory buffer to inform future attempts and avoid repeating the same errors [[3]]. This demonstrates how the loop can enable a form of learning from experience within the agent's logic. The pattern is particularly effective when clear, objective evaluation criteria exist, as this allows for systematic and predictable improvement [[1,2]].

However, the effectiveness of the Evaluator-Optimizer Loop is contingent on several factors. First, the quality of the final output is directly tied to the quality of the evaluation criteria and the evaluator itself [[2]]. If the criteria are subjective or inconsistent, the feedback loop may become unreliable [[2]]. A significant risk is the "Yes-Man Problem," where the evaluator and generator are the same model or trained on similar data, leading to confirmation bias and correlated failures where the flawed output is confidently approved [[39,41]]. A structural fix for this involves using different models for the generator and evaluator or providing the evaluator with a strict, measurable rubric [[39,42]]. Another critical consideration is cost management. Each iteration adds to the total token consumption and latency, so the trade-off between quality gain and computational expense must be carefully evaluated [[2,52]]. Hard limits on the number of refinements (`max_refinements`) and budgets on token usage are essential guardrails to prevent resource exhaustion and infinite loops [[51,52]]. Without these safeguards, the system could get stuck in a state of perpetual revision, degrading the quality of the output over time [[3]].

In the domain of web agents, the Evaluator-Optimizer Loop finds numerous practical applications. One primary use case is in Retrieval-Augmented Generation (RAG) and information extraction. An agent tasked with finding answers from a set of documents can use an optimizer to generate a search query. The evaluator can then assess the relevance of the retrieved documents; if they are poor, the loop refines the query for another attempt [[33]]. This iterative retrieval process, known as Corrective RAG (CRAG), enhances the quality of the context provided to the final answer-generating LLM [[33]]. Another application is in validating structured data extraction from web pages. An optimizer agent extracts data into a JSON format, and an evaluator agent verifies that the output conforms to a predefined schema and contains no factual contradictions [[42]]. If the schema check fails, the optimizer is fed the error message and tries again. This ensures high-fidelity data entry, which is critical for downstream business processes. The Planner-Validator architecture used by the Skyvern 2.0 web agent was instrumental in boosting its performance on the WebVoyager benchmark from 45% to 85.85% by adding a dedicated validator to confirm that planned actions successfully executed [[45]]. DSPy, a framework for building optimized AI systems, treats optimization and evaluation as first-class citizens, using algorithms to automatically tune prompts and few-shot examples by repeatedly running the optimizer and evaluating its performance against a metric [[28,29]]. This highlights the pattern's utility not just for post-hoc correction but for proactive prompt engineering. The loop provides a robust mechanism for enforcing domain-specific quality gates, ensuring that outputs meet stringent standards before being delivered or used in subsequent automated steps [[51]].

## DAG Orchestrators: Structured Workflow Management for Predictable Execution

DAG Orchestrators represent a class of workflow management systems that utilize Directed Acyclic Graphs (DAGs) to define, schedule, and execute a series of dependent tasks [[20,47]]. In this architectural pattern, nodes in the graph represent individual tasks or jobs, while directed edges symbolize dependencies, dictating that a given task cannot start until its predecessor(s) have completed [[13,37]]. The "acyclic" constraint is a defining feature, ensuring that no path in the graph loops back on itself, which mathematically guarantees that any given workflow will eventually terminate [[12,13]]. This focus on acyclicity prioritizes determinism, predictability, and reliability, making DAG orchestrators ideal for managing structured, repeatable, and often long-running processes [[4,8]]. This pattern is widely used in data engineering for ETL (Extract, Transform, Load) pipelines and batch processing, and its principles are increasingly being applied to AI workflows to bring structure and control to complex agentic systems [[4,20]]. Prominent examples of tools that embody this pattern include Apache Airflow, Dagster, Prefect, and AWS Step Functions [[37,47]].

The primary function of a DAG orchestrator is to automate and manage the lifecycle of a workflow [[47]]. The developer defines the entire workflow as a static blueprint, often in a configuration file or a programming language like Python [[4]]. The orchestrator engine then takes over, scheduling the execution of nodes according to their dependencies. When a node becomes eligible (i.e., all its upstream dependencies are satisfied), the scheduler dispatches it for execution, typically on a distributed pool of worker executors [[47]]. A key strength of the DAG model is its inherent support for parallelization. Any nodes that have no dependency on each other's output can be executed concurrently, significantly reducing the total wall-clock time for a workflow, especially when those tasks are independent and computationally intensive [[13,15]]. For example, in a GTM (Go-To-Market) workflow, enriching company data and scoring a lead can happen in parallel after the initial lead information is received, cutting down the overall processing time [[13]]. This contrasts sharply with linear chains, where all tasks must be executed sequentially, leading to artificial serialization and wasted time [[15]].

State management in DAG orchestrators is typically handled at the engine level. The orchestrator maintains the global state of the workflow, tracking the status of each node (e.g., queued, running, success, failed) [[47]]. Data can be passed between nodes using specific mechanisms. For example, Apache Airflow uses XComs (cross-communications) for passing small amounts of data, while larger datasets might be stored in an external data store like a database or cloud storage bucket and referenced by subsequent nodes [[47]]. While some modern DAG frameworks like Prefect offer more dynamic capabilities, such as dynamic task mapping where new tasks can be created at runtime based on upstream data, the core paradigm remains centered on a pre-defined or semi-static topology [[47]]. This static nature is both a strength and a limitation. It provides predictability and makes workflows easier to test and reason about, but it can be rigid when faced with unexpected events or when the optimal workflow path is only known at runtime [[15,37]].

Fault tolerance is a cornerstone of production-grade DAG orchestrators. When a node fails, the orchestrator's default behavior is to halt the execution of its dependent nodes, preventing them from operating on potentially invalid data [[15]]. Modern orchestrators provide robust mechanisms for recovery. With idempotent tasks and persistent state, the system can be configured to retry only the failed node, replaying its inputs and re-executing the logic without needing to re-run the entire preceding chain of successful tasks [[15,47]]. This partial failure recovery is a significant efficiency gain. Platforms like Temporal.io are explicitly designed around this principle of durable execution, treating the entire workflow as a resilient entity that can survive process crashes and network partitions by persisting its state and replaying its logic from a safe point [[48]]. Additional fault-tolerance features include automatic retries with exponential backoff for transient errors, circuit breakers to prevent cascading failures to downstream services, and compensation steps to roll back partial completions in case of a major failure, a pattern known as Saga [[7,37]]. Human-in-the-loop (HITL) checkpoints are also a common feature, where a workflow can be paused at a specific node to await manual approval before proceeding, which is critical for high-stakes or regulatory tasks [[7,37]].

For multi-agent web systems, DAG Orchestrators are highly suitable for tasks that can be decomposed into a predictable, structured pipeline. For instance, a workflow for monitoring e-commerce product availability could be modeled as a DAG with nodes for fetching the product page, parsing the price and stock status, comparing the new data with a historical record, and sending an alert if a change is detected [[20]]. This type of sequential, rule-based process is a classic use case for a DAG. The ability to run independent sub-tasks in parallel is also beneficial; for example, an agent could be tasked with gathering competitor pricing from multiple websites, and each website's scraping task could be an independent node in the graph [[13]]. However, the rigidity of the acyclic constraint makes DAGs less ideal for exploratory or highly interactive web tasks where the next step is not known in advance [[4]]. In a scenario requiring autonomous navigation through a complex, dynamic website, the fixed dependency structure of a traditional DAG can become a bottleneck. The system might encounter an unexpected CAPTCHA or a dynamically loaded menu, requiring a deviation from the pre-planned path that a static DAG cannot easily accommodate. For such tasks, a more dynamic orchestration model like a State Graph is often preferred [[4]]. Nonetheless, hybrid approaches are emerging where a high-level DAG orchestrator manages the overall job, while a more flexible, internal orchestrator (like LangGraph) handles the dynamic sub-processes within a single node of the DAG [[15]]. This allows organizations to leverage the strengths of both paradigms, combining the predictability and scalability of DAGs for macro-management with the adaptability of state graphs for micro-control.

Each architecture represents a distinct philosophy on how to manage the complexity of multi-agent systems, and their effectiveness depends heavily on the requirements of the application.

One of the most significant distinctions lies in their approach to control flow and adaptability. State Graphs offer the highest degree of flexibility, functioning as a programmable state machine where the execution path can be altered dynamically at every step [[36]]. This is enabled by conditional edges that inspect the current state and reroute execution accordingly, and by the explicit support for cycles that allow for looping and self-correction [[11,12]]. This makes them exceptionally well-suited for the unpredictable nature of the web, where an agent might need to handle unexpected pop-ups, wait for asynchronous content, or backtrack due to an incorrect click. In contrast, the Evaluator-Optimizer Loop provides a more constrained form of adaptability. Its "loop" is a fixed pattern of refinement, and while it adapts by trying again, the underlying logic for how it tries again is determined by the feedback mechanism, not by a dynamic re-planning of the entire workflow [[3]]. DAG Orchestrators prioritize predictability above all else. Their control flow is typically static, defined at author time, which ensures that workflows are deterministic and reliable but sacrifices the ability to adapt to unforeseen circumstances during execution [[8,37]]. This makes them ideal for batch-oriented tasks but less suitable for real-time, exploratory web interactions.

State management is another critical area of divergence. State Graphs employ a centralized, shared state object that acts as the single source of truth for the entire graph [[16]]. This simplifies context sharing among multiple agents acting as nodes, as they all read from and write to the same data structure [[32]]. The integration with external checkpointers ensures this state is durable, forming the basis for fault tolerance [[6]]. The Evaluator-Optimizer Loop's state management is more narrowly focused on the artifact being refined and its history of attempts [[51]]. While persistence is still important for audit trails, the scope of managed state is smaller. DAG Orchestrators manage state at the engine level, tracking the status of each task and facilitating data exchange between them [[47]]. This centralized engine-based state management is robust and scalable for large numbers of concurrent workflows, but it abstracts away the details of inter-task data flow, which can sometimes make debugging more opaque compared to the explicit state object in LangGraph [[20]].

From a fault tolerance perspective, all three architectures provide mechanisms to handle failures, but with different levels of sophistication. State Graphs stand out with their rich, built-in primitives like `RetryPolicy` for transient errors, `TimeoutPolicy` to prevent hangs, and dedicated `error_handler` nodes for compensation logic, allowing for the implementation of advanced patterns like the Saga pattern for partial rollbacks [[35]]. The foundation of this resilience is the persistent state that allows for precise resumption from the point of failure [[36]]. Evaluator-Optimizer Loops rely on simpler but effective guardrails. The primary mechanism is a hard cap on the number of refinement iterations (`max_refinements`) and a fallback strategy, which prevents runaway costs and infinite loops if the generator is unable to satisfy the evaluator [[51,52]]. DAG Orchestrators are inherently resilient due to their dependency model. A failed node simply blocks its dependents, and with idempotent tasks and checkpointing, the system can efficiently retry only the failed component [[15]]. They also incorporate standard enterprise patterns like circuit breakers and scheduled retries to enhance reliability [[7]].

Finally, their suitability for web-agent tasks reflects these underlying differences. State Graphs are arguably the best fit for complex, multi-step web interactions that require a high degree of autonomy and state awareness, such as deep research, complex data extraction, or conversational customer service bots [[31,50]]. The ability to model browser actions as nodes and use conditional logic to react to page states makes them a powerful tool for building robust web agents [[43]]. Evaluator-Optimizer Loops are most valuable as a quality gate within a larger system. They excel at tasks where the correctness of the output can be formally verified, such as ensuring extracted data conforms to a schema, generating code that passes unit tests, or producing text that adheres to a strict style guide [[9,42]]. They are a tool for enhancing fidelity, not necessarily for planning the overall journey. DAG Orchestrators are best suited for more structured and repetitive web automation tasks, like monitoring websites for price changes, scraping public data from multiple sources, or executing a standardized workflow across a large number of web pages [[4,20]]. Their strength in parallelizing independent tasks makes them efficient for bulk operations, but their rigidity can be a liability in more exploratory scenarios.

## Practical Implementation Considerations and Failure Modes

While State Graphs, Evaluator-Optimizer Loops, and DAG Orchestrators offer powerful abstractions for building multi-agent web systems, their practical implementation in production environments introduces a host of challenges and potential failure modes that must be carefully managed. These range from architectural complexities and state synchronization issues in distributed systems to the pervasive problem of debugging non-deterministic behavior and managing escalating costs.

A primary challenge, particularly for State Graph-based systems like LangGraph, is the transition from a monolithic, single-node application to a distributed, multi-agent environment [[22]]. In a single-node setup, a shared in-memory state object works effectively. However, when agents are deployed across different cloud regions or edge nodes, this model collapses, leading to catastrophic issues like split-brain scenarios, race conditions, lost updates, and desynchronized routing paths [[22]]. Solving this "distributed context management problem" is analogous to tackling data consistency in microservices architectures [[22]]. Two main technical approaches emerge for synchronizing state across distributed agents. The first is pessimistic concurrency control using distributed locking, where an agent must acquire an exclusive lease (using tools like Redis or ZooKeeper) before modifying a shared state key [[22]]. While this ensures safety, it introduces severe latency bottlenecks, as other agents are blocked from proceeding until the lock is released, making it suitable only for accessing exclusive resources like a single browser instance [[22]]. The second, more scalable approach is optimistic concurrency control using Conflict-free Replicated Data Types (CRDTs). CRDTs are mathematical data structures that can converge to the same value across all replicas without requiring locks, even if updates arrive out of order [[22]]. This allows for high-concurrency writes and is highly resilient to network partitions, making it ideal for collaborative contexts like shared memory graphs or logs of tool outputs [[22]]. Implementing a robust distributed system thus requires a sophisticated stack with a synchronization layer (like CRDTs or locks) and a persistence layer that uses event sourcing to record every state transition, enabling state rehydration after a node failure [[22]].

Regardless of the orchestration architecture, debugging and observability are formidable hurdles in production agentic systems [[18,37]]. The non-deterministic nature of LLMs means that even with a deterministic control flow, the outputs can vary between runs, complicating reproduction and analysis of failures [[8]]. A silent agent failure, where an agent stalls or crashes without signaling its state, is a notorious problem that can cause downstream agents to wait indefinitely, leading to cascading failures and wasted resources [[5]]. A proposed "minimum stack" for reliable orchestration includes explicit DAGs for workflow definition, hard timeouts, bounded retries, and comprehensive logging and visibility into every stage of the process [[5]]. Tools like LangSmith are integral to making these systems manageable, providing features like time-travel debugging, visualization of execution traces, and detailed telemetry on LLM calls, costs, and latencies [[14,31]]. Without such deep observability, pinpointing the root cause of a failure—a corrupted state transition, a misconfigured prompt, or a stalled external API call—becomes nearly impossible [[18]]. The context window problem is another subtle but critical failure mode; as tasks pass between multiple agents, the accumulated context can rapidly fill the LLM's input capacity, causing it to silently drop critical information and produce flawed outputs [[19]].

Cost management is a pervasive concern across all three architectures, but it is most acute for Evaluator-Optimizer Loops and complex State Graphs. The Evaluator-Optimizer pattern directly trades computational cost for higher-quality results, multiplying the number of LLM calls required for a single piece of output [[2]]. An experiment reported that a multi-agent system could consume up to 15 times more tokens than a single-agent chat session to achieve the same objective, highlighting the economic viability challenge for high-volume applications [[24]]. Even State Graphs, despite their efficiency gains from partial execution and parallelism, introduce overhead from frequent state checkpointing and the complexity of managing multiple agents [[34]]. Unnecessary architectural overhead can also arise; using a heavyweight framework like LangGraph for a simple, linear task is inefficient, just as using a rigid DAG for a highly exploratory task is ineffective [[4,33]]. Therefore, a crucial implementation consideration is to align the architectural pattern with the specific needs of the task, avoiding over-engineering.

Beyond architectural patterns, there are common failure modes related to the agents themselves. The "self-consistency trap" occurs when an LLM generates plausible but factually incorrect content with high confidence, fooling a self-evaluation mechanism [[3]]. Mitigation requires grounding reflection in external tools or verifiable data sources [[3]]. Another issue is sycophantic reflection, where an agent agrees with its own output rather than critiquing it honestly [[3]]. Using different models or configurations for generation versus evaluation can help counteract this [[3]]. In self-correcting loops, a significant failure mode is the "Yes-Man Problem," where the generator and evaluator share the same blind spots, leading the system to stay confidently wrong [[39,41]]. Using separate models for these roles is a recommended structural fix [[39]]. Finally, cascading errors are a major risk in multi-agent systems. A small mistake made by an early agent gets propagated through the system, corrupting the shared state and affecting every subsequent step [[19,39]]. In a 10-step pipeline with a 95% per-step success rate, the overall probability of success plummets to around 60% [[39]]. Effective mitigation strategies include maintaining immutable logs of raw outputs, implementing backward tracing to roll back to a clean state upon failure, and designing agents to be resilient to minor corruptions in the incoming context [[39]]. Addressing these practical challenges requires a holistic approach that combines robust architectural choices with a strong foundation of observability, cost controls, and defensive design principles.

## Synthesis and Strategic Recommendations for Web-Agent Design

The comparative analysis of State Graphs, Evaluator-Optimizer Loops, and DAG Orchestrators reveals that these are not merely alternative frameworks but fundamentally different architectural philosophies for managing the complexity inherent in multi-agent web systems. The optimal choice is not a matter of declaring one superior to the others, but rather of understanding their respective strengths and weaknesses and aligning them with the specific demands of the task at hand. The overarching theme is a recurring trade-off between flexibility and determinism: State Graphs offer maximum flexibility for dynamic, interactive tasks; Evaluator-Optimizer Loops provide targeted quality assurance for verifiable outputs; and DAG Orchestrators deliver predictable, scalable execution for structured, repeatable processes.

**State Graphs**, exemplified by LangGraph, serve as the most granular and powerful orchestration control plane. Their primary value lies in their ability to provide explicit, programmable control over a system's state and control flow, enabling the construction of complex, resilient, and adaptive agentic behaviors [[16,36]]. The native support for cycles and conditional edges allows for the modeling of iterative refinement, self-correction, and dynamic decision-making, making them exceptionally well-suited for complex, non-linear web interactions such as autonomous research, data extraction from dynamic sites, and sophisticated customer service workflows [[31,43]]. The integrated checkpointing and rich fault-tolerance primitives provide a robust foundation for building production-grade systems that can recover from failures without losing progress [[35,36]]. However, this power comes with increased complexity and a steeper learning curve, making them potentially overkill for simpler tasks [[33]]. They are the go-to choice when the control logic itself is a critical component of the solution.

**Evaluator-Optimizer Loops** represent a higher-level quality assurance pattern rather than a complete orchestration framework. Its strategic purpose is to enforce fidelity and correctness through a dedicated cycle of iterative refinement [[1,2]]. This pattern is invaluable for tasks where the output must adhere to strict, verifiable standards. In a web-agent context, this translates to validating extracted data against a schema, ensuring generated code passes tests, or progressively improving search queries based on relevance feedback [[33,42]]. The primary trade-off is a direct increase in computational cost and latency, as the loop adds multiple LLM calls for each final output [[2]]. This cost must be justified by the quality gains, necessitating careful budgeting and the implementation of hard iteration limits to prevent resource exhaustion [[51,52]]. This pattern should be viewed as a specialized tool for enhancing the quality of specific artifacts within a broader agent system, not as a replacement for the overarching orchestration logic.

**DAG Orchestrators** provide a structured, deterministic approach to workflow management, prioritizing predictability, parallelization, and reliability [[4,47]]. Their acyclic constraint ensures that workflows have a definite end, making them highly reliable for managing long-running, batch-oriented processes [[12]]. They excel at automating structured web tasks that can be broken down into a clear sequence of dependent steps, such as data scraping campaigns, routine monitoring, or ETL-style data pipelines [[13,20]]. The ability to run independent tasks in parallel significantly reduces wall-clock time, and their inherent fault isolation and recovery mechanisms make them a solid choice for enterprise-scale automation [[7,15]]. The main drawback is their rigidity; the fixed workflow topology can be a significant limitation for exploratory or highly interactive tasks where the next step is not known in advance [[4]]. They are best employed for tasks that are predictable, repeatable, and benefit from parallel execution.

Given these distinct characteristics, a strategic recommendation for designing modern web-agent systems is to embrace hybrid approaches that leverage the strengths of each pattern. Rather than choosing one exclusively, architects can compose systems that use a DAG orchestrator at a high level to manage large-scale, scheduled jobs. Within a single node of that DAG, a State Graph could be used to orchestrate a team of specialized agents performing a complex, interactive sub-task. Inside one of those agents' roles, an Evaluator-Optimizer loop could be invoked to ensure the final output meets stringent quality and correctness criteria. This layered, compositional approach allows for the best of all worlds: the scalability and scheduling of DAGs, the dynamic control and fault tolerance of State Graphs, and the quality assurance of Evaluator-Optimizer loops. Ultimately, the path to building robust, reliable, and effective web agents in production requires moving beyond simplistic, linear agent chains and adopting a deliberate orchestration strategy. The choice of pattern—State Graph, Evaluator-Optimizer Loop, or DAG Orchestrator—should be guided by a clear understanding of the task's requirements for flexibility, predictability, and quality, recognizing that the most powerful systems will likely integrate these complementary architectural styles.
