# Architectural Choices for Web Agents: A Comparative Guide to State Graphs, Evaluator-Optimizer Loops, and DAG Orchestrators

## Core Architectural Paradigms: State Graphs, Loops, and DAGs

The design of multi-agent LLM systems for web interactions involves making fundamental decisions about how to structure and orchestrate the behavior of multiple specialized components. Three dominant paradigms have emerged from current practice: State Graphs, Evaluator-Optimizer loops, and Directed Acyclic Graph (DAG) Orchestrators. Each represents a distinct philosophy for managing complexity, controlling execution, and enabling collaboration among agents. Understanding their foundational principles is essential for selecting the appropriate architecture for a given web automation task. These paradigms range from highly explicit and controllable finite state machine-like models to tightly coupled feedback loops focused on quality assurance and structured, acyclic data pipelines optimized for efficiency.

The State Graph paradigm, most prominently embodied by the LangGraph framework, is rooted in the concept of a Finite State Machine (FSM) [[10]]. This approach models an agent workflow as a directed graph where computational steps are represented as "nodes" and transitions between them as "edges" [[1,37]]. The defining characteristic of this model is the introduction of a shared, persistent "state" object—a central data structure like a Pydantic model or `TypedDict`—that flows through the entire graph [[1,39]]. Every node can read from this shared state and write updates back to it, creating a collaborative environment where all agents have access to a common snapshot of the application's progress [[2,20]]. This explicit, code-defined structure provides maximum transparency and control over the entire process, making it particularly well-suited for complex, deterministic workflows where auditability and precise management of every step are paramount [[12,32]]. The ability to define cycles allows for sophisticated agentic behaviors such as iterative refinement, self-correction, and dynamic routing based on runtime conditions [[9,10]].

In contrast, the Evaluator-Optimizer loop is not primarily an orchestrator for a diverse set of independent agents but rather a dedicated feedback control mechanism for improving the quality of a single output stream [[4]]. Its philosophical basis is iterative refinement, trading increased computational cost and latency for higher fidelity and correctness [[26]]. The core of the pattern involves a simple `while True` loop that continues until an evaluation passes or a predefined maximum number of iterations is reached [[4,6]]. This pattern typically involves two distinct components: a "Generator" that produces an initial solution and an "Evaluator" that assesses it against explicit criteria [[7]]. The separation of these roles is a key differentiator from self-reflection patterns, where a single model critiques its own output [[24]]. By using a separate evaluator, the architecture avoids confirmation bias and enables more rigorous, objective feedback, potentially using different models or external tools for evaluation [[6,41]]. This makes it a powerful tool for quality assurance, fact-checking, and goal-oriented problem-solving where measurable improvement is possible with specific feedback [[7,40]].

The third paradigm, DAG Orchestrators, draws inspiration from traditional workflow engines and data processing pipelines [[15,22]]. A Directed Acyclic Graph represents a workflow as a set of tasks (nodes) with explicit dependencies (edges). The primary advantage of this model is its natural support for parallelism; independent tasks can execute concurrently while dependent tasks are executed in a predictable, topologically sorted order [[15]]. This approach prioritizes efficiency, predictability, and scalability for well-defined processes. Tools like Microsoft's Conductor exemplify this by allowing developers to define the entire workflow topology statically in a YAML file before execution begins [[16]]. This static definition makes the control flow explicit at author time, contrasting with dynamic approaches where an LLM planner determines the path at runtime [[30]]. Because the graph is acyclic, it inherently prevents infinite loops, which simplifies reasoning about termination. However, this constraint also makes expressing iterative logic natively difficult, often requiring special loop-back patterns to be implemented [[16,30]]. This architecture is ideal for business-critical workflows where the execution path is known in advance and needs to be guaranteed, offering deterministic execution and automatic parallelization of independent branches [[12,15]].

| :--- | :--- | :--- | :--- |
| **State Graphs** | Finite State Machine (FSM) with a shared, persistent state [[1,10]] | Complex, adaptive, long-running workflows requiring explicit control, loops, and human-in-the-loop review [[3,34]] | Explicit, code-defined control flow with dynamic routing and full state management via a shared data structure [[2]] |
| **Evaluator-Optimizer Loops** | Feedback control mechanism for iterative refinement [[4]] | Tasks requiring high-quality outputs through repeated generation and evaluation, such as code generation or content creation [[6,40]] | A tight, closed-loop cycle separating generator and evaluator roles to provide objective feedback and avoid confirmation bias [[6,24]] |
| **DAG Orchestrators** | Structured workflow engine with explicit dependencies [[15,22]] | Well-defined, repeatable processes where maximizing throughput through parallelism is critical [[13,15]] | Static or dynamically determined acyclic graph topology that guarantees termination and enables automatic parallelization of independent tasks [[15,16]] |

## Control Flow and Agent Coordination Mechanisms

The mechanisms by which each architecture directs the sequence of operations and facilitates interaction among agents are central to their operational differences. State Graphs offer granular, dynamic control; Evaluator-Optimizer loops enforce a rigid, linear refinement cycle; and DAG Orchestrators provide a structured, often static, model for task execution. These differing approaches to control flow directly influence how tasks are decomposed, how agents collaborate, and the overall flexibility of the resulting system.

State Graph architectures, exemplified by LangGraph, provide the most flexible and dynamic control flow. While they can model simple sequential chains, their true power lies in their ability to implement complex, non-linear logic explicitly through conditional edges [[1]]. A developer can define a routing function that inspects the current state and returns the name of the next node to execute, allowing the workflow to branch based on intermediate results [[2,39]]. This enables sophisticated patterns like retrying failed steps, attempting alternative solutions, or routing to different agents based on user input. Furthermore, nodes themselves can return a `Command` object containing navigation instructions (`goto`), allowing for immediate, fine-grained control over the execution path without waiting for the next super-step [[1]]. This FSM-like model supports a wide range of agent coordination strategies. The most common is the hierarchical Supervisor-Worker pattern, where a central supervisor node analyzes a task and routes it to one of several specialized worker nodes [[10,37]]. Workers perform their tasks, update the shared state, and return control to the supervisor, which then decides the next action [[10]]. This creates a clear line of authority and control. Other patterns include multi-agent collaboration where agents share a common scratchpad of messages, or more complex hierarchical teams where subagents are other LangGraph objects themselves [[9]]. This explicit, code-driven approach gives developers ultimate control over the coordination logic, but it also requires careful design to avoid creating overly complex or unmanageable graphs [[3]].

The Evaluator-Optimizer loop, by contrast, has a very constrained and rigid control flow. It is fundamentally a linear, synchronous cycle defined by a `while True` loop [[4]]. The sequence is always: Generate → Evaluate → Check Termination Condition → Revise/Repeat [[6]]. There is no inherent branching or parallelism within the loop itself; the entire mechanism is focused on refining a single output stream until it meets a predefined quality threshold [[6,26]]. Consequently, its agent coordination strategy is minimalistic. It typically involves only two agents: a Generator that creates the initial output and an Evaluator that immediately consumes it for critique [[6,7]]. Their interaction is tightly coupled and sequential. The feedback generated by the Evaluator is passed directly back to the Generator to inform the next revision [[6]]. In some implementations, a third "fixer" or "optimizer" agent may be introduced to handle the revision phase, but the overall coordination remains a simple, closed-loop process [[8,25]]. This simplicity ensures predictability but severely limits its applicability to broader, multi-agent collaborative tasks where delegation and parallel work are required.

DAG Orchestrators provide a highly structured and predictable control flow, prioritizing determinism and efficiency. The workflow's topology is defined upfront, either in a declarative format like YAML (as in Microsoft's Conductor [[16]]) or through an API call [[22]]. Execution proceeds according to a topological sort of the graph, ensuring that a node only runs after all its predecessor nodes have completed [[15]]. This model naturally supports parallelism; independent nodes that have no dependencies on each other can be executed simultaneously, significantly reducing end-to-end latency for suitable workflows [[15]]. Conditional routing is supported through predicates on edges, which can direct execution down different paths based on the outcome of upstream tasks [[15]]. This allows for basic branching logic, such as implementing a fallback path if a primary operation fails [[15]]. The coordination patterns enabled by this architecture are diverse. The "Fan-out/Fan-in" pattern is a classic example, where a planning node dispatches multiple independent worker nodes to run in parallel, and a subsequent synthesis node waits for all of them to complete before aggregating the results [[15]]. Hierarchical Orchestration is also well-supported, often implemented as a Router pattern where a lightweight agent classifies a request and directs it to the appropriate specialist agent [[14,38]]. Some systems like Conductor enforce strict context isolation between agents to prevent unintended side effects, requiring explicit dependency management for inter-node communication [[16]]. This structured approach makes DAGs excellent for business-critical workflows where the path is known and needs to be guaranteed, though it can be less flexible than state graphs for ad-hoc decision-making [[12]].

| Dimension | State Graphs (e.g., LangGraph) | Evaluator-Optimizer Loops | DAG Orchestrators (e.g., Conductor) |
| :--- | :--- | :--- | :--- |
| **Primary Control Flow Mechanism** | Conditional edges, `Command` objects, and routing functions that make dynamic decisions based on the shared state [[1,2]]. | A fixed `while True` loop that continues until a success condition is met or a maximum iteration count is reached [[4,6]]. | Topological sorting of a pre-defined graph structure, which automatically handles dependencies and parallelism [[15]]. |
| **Branching & Looping** | Highly dynamic and explicit. Supports arbitrary conditional branching and looping through cycles in the graph [[9,10]]. | Linear and fixed. No inherent branching; the loop refines a single output stream sequentially [[6]]. | Supported via conditional edges with predicates, but the overall structure remains acyclic without special loop-back patterns [[15,16]]. |
| **Typical Coordination Pattern** | Hierarchical (Supervisor-Worker), Multi-Agent Collaboration, and Subgraphs for encapsulation [[9,10]]. | Critic-Refiner (or Writer-Editor-Rewrite), a closed-loop system with a minimal number of tightly coupled agents [[6,24]]. | Fan-out/Fan-in (Parallel Execution), Hierarchical Orchestration (Manager-Workers), and Router patterns [[13,22]]. |
| **Agent Communication** | Through a shared state object that all nodes can read from and write to, providing a common memory space [[20,39]]. | Synchronous and direct. The Generator passes its output to the Evaluator, which passes feedback directly back to the Generator [[6]]. | Typically stateless per request, with communication handled through explicit context passing or shared knowledge spaces (blackboard) [[16,17]]. |
| **Flexibility vs. Determinism** | High flexibility for dynamic, adaptive workflows, but risks complexity and lack of guarantee of termination if not designed carefully [[3,10]]. | Low flexibility; highly deterministic in its purpose but rigid in its implementation [[6]]. | High determinism due to static topology, but less flexible for tasks requiring emergent or unplanned paths [[16,22]]. |

## State Management, Persistence, and Error Handling

Effective state management and robust fault tolerance are critical for building reliable, production-grade web-agent systems. The three architectural paradigms approach these challenges with different philosophies and toolsets. State Graphs provide the most integrated and sophisticated mechanisms for managing complex, evolving states and handling errors gracefully. Evaluator-Optimizer loops rely on simpler, hard-coded termination conditions. DAG Orchestrators leverage the inherent properties of their acyclic structure to enable partial recovery and configurable failure policies. The choice of architecture thus has profound implications for the resilience and debuggability of the final application.

State Graph architectures offer the most advanced and native support for state management and fault tolerance. At their core is a shared state object, typically defined with a strict schema using a Pydantic model or `TypedDict`, which acts as the system's persistent memory [[1,12]]. This explicit state is passed to every node, and updates are merged using reducers, which can be configured to overwrite values, append items to lists, or even clear fields entirely [[1,10]]. This provides fine-grained control over how information accumulates and evolves throughout the workflow. For fault tolerance, LangGraph provides first-class primitives. Developers can attach a `RetryPolicy` to any node, which automatically handles retries with exponential backoff and jitter for transient errors like network timeouts [[19,21]]. A `TimeoutPolicy` can be used to prevent a hung node from blocking the entire workflow [[19]]. Most importantly, LangGraph supports a dedicated `error_handler` node that is invoked only after all retries for a specific node have been exhausted [[19]]. This handler receives the full context of the failure, including the exception type and message, and can execute compensation logic, such as rolling back partial side effects, thereby implementing patterns like Saga for maintaining data consistency in distributed systems [[19]]. Persistence is handled through "checkpointers," which save the entire state to a durable backend (like Postgres or Redis) after every node execution [[10,20]]. This enables long-running jobs to resume from the exact point of failure and supports human-in-the-loop workflows where execution can be paused for manual intervention [[20,37]]. Error propagation is managed by simply adding an `errors` field to the shared state, allowing downstream nodes to inspect the history of failures and react accordingly [[21]].

The Evaluator-Optimizer loop relies on much simpler mechanisms for state management and error handling. The state is implicitly managed within the variables of the Python function that implements the loop. There is no built-in, framework-level support for sophisticated fault tolerance. The primary mechanism for preventing runaway processes is a manually coded maximum iteration limit, which serves as a circuit breaker to terminate the loop [[8,27]]. While individual generation or evaluation steps could be wrapped in standard Python `try/except` blocks to catch specific exceptions, there is no native infrastructure for automated retries, timeouts, or fallback paths [[21]]. If an evaluation step fails due to a malformed prompt or a temporary service outage, the entire loop would typically crash unless this logic is explicitly implemented by the developer. Similarly, if the generator fails to produce a valid response, the loop might continue indefinitely if the termination condition is not properly defined, leading to a waste of computational resources [[7,28]]. This reliance on manual implementation makes the pattern less resilient out-of-the-box compared to frameworks like LangGraph, placing a greater burden on the developer to engineer safety and reliability into the loop's logic.

DAG Orchestrators leverage the mathematical properties of their underlying graph structure to achieve resilience and efficient state management. Because execution follows a topological order, the system inherently knows which tasks are ready to run and which are blocked by dependencies [[15]]. This structure is particularly advantageous for partial failure recovery. If a single node in a DAG fails, only that specific task needs to be retried; other independent branches of the graph that were executing in parallel can continue unaffected, and once the failed task succeeds, execution can proceed from there [[15]]. This is a significant improvement over linear chains, where a single failure can halt the entire process [[15]]. Systems like Microsoft's Conductor provide configurable failure modes for parallel groups, such as `fail_fast` (stopping all executions on the first error) or `continue_on_error` (allowing other parallel tasks to finish), giving developers fine-grained control over fault propagation [[16]]. State management is often handled by passing data explicitly between nodes or through a shared knowledge space [[17]]. Some orchestrators enforce strict context control modes to prevent "conversation bleeding" between unrelated tasks, which can reduce token costs and prevent unintended side effects [[16]]. While the DAG model provides a strong foundation for fault tolerance, the specific capabilities depend heavily on the underlying engine (e.g., Airflow, Prefect, Dagster) and may require integration with additional tools for features like durable state persistence or human-in-the-loop interventions [[15]].

| Feature | State Graphs (e.g., LangGraph) | Evaluator-Optimizer Loops | DAG Orchestrators (e.g., Conductor) |
| :--- | :--- | :--- | :--- |
| **State Representation** | Explicit, shared, and strictly typed (Pydantic, `TypedDict`) state object updated by all nodes [[1,12]]. | Implicit state managed within local variables of the loop's function. | Often stateless per task, with data passed explicitly between nodes or stored in external memory [[16]]. |
| **Persistence Mechanism** | Integrated checkpointing to durable backends (e.g., Postgres, Redis) after every step, enabling pause/resume [[10,20]]. | Manual implementation required (e.g., saving variables to a database). | Depends on the underlying engine; many support durable execution histories for recovery [[30]]. |
| **Fault Tolerance Primitives** | Native support for `RetryPolicy`, `TimeoutPolicy`, and dedicated `error_handler` nodes for compensation logic [[19]]. | Relies on manual `try/except` blocks and a hard-coded maximum iteration limit as a circuit breaker [[8,28]]. | Leverages the acyclic graph structure for partial failure recovery. Configurable group-level failure policies (`fail_fast`, etc.) [[15,16]]. |
| **Error Propagation** | Explicitly managed via a dedicated `errors` list in the shared state, which downstream nodes can inspect [[21]]. | Handled by the enclosing `try/except` block or leads to a complete loop termination. | Managed through the dependency graph; failures can block downstream tasks but not necessarily halt the entire workflow [[15]]. |
| **Resilience Features** | Time-travel debugging, scenario exploration by rewinding and modifying state, and robust human-in-the-loop support [[3,10]]. | Limited resilience; lacks native support for graceful degradation or sophisticated retry strategies [[7]]. | Automatic parallelization of independent branches, allowing unaffected work to continue during partial failures [[15]]. |

## Scalability, Performance, and Production Trade-offs

The choice of an architectural pattern has significant implications for the scalability, performance, and overall cost-effectiveness of a multi-agent web-agent system. State Graphs, with their focus on explicit control and statefulness, can introduce performance overhead and complexity. Evaluator-Optimizer loops are inherently expensive due to their iterative nature, making them suitable only when quality gains justify the cost. DAG Orchestrators excel at optimizing for performance in parallelizable workflows but can be less flexible for tasks requiring iterative refinement. Understanding these trade-offs is crucial for designing systems that are not only functional but also efficient and economically viable.

State Graph architectures, while powerful, can introduce notable performance overhead. The requirement for persistent state management means that every step in the graph should ideally be checkpointed, which adds latency as the system writes to a durable storage backend [[3,20]]. This stateful nature can lead to issues like "State Explosion," where the shared state object grows uncontrollably large with conversation history, search results, and intermediate outputs, degrading performance and increasing token usage [[17,18]]. Concurrent execution in a state graph is possible but must be explicitly modeled. When parallel nodes operate on the same shared state, there is a risk of race conditions if updates are not properly synchronized, requiring careful design to manage concurrency safely [[15]]. From a cost perspective, each agent call in a state graph represents another API call to an LLM, and in parallel branches, the same context may be duplicated, multiplying token consumption [[12,17]]. Therefore, while LangGraph is well-suited for complex, stateful workflows, its use should be justified by the need for its specific features, as simpler deterministic services might be more efficient for parts of the logic [[3]].

Evaluator-Optimizer loops are inherently costly in terms of both latency and monetary expense. The iterative refinement process means that the system performs multiple LLM calls (one for generation and one for evaluation) for each pass through the loop [[7]]. This continues until a success condition is met, which could take anywhere from one to many iterations. This makes the pattern expensive, with the total cost being variable and dependent on the difficulty of the task and the quality of the initial output [[7]]. Latency is similarly affected, as each iteration adds round-trip time to the LLM and evaluation process [[6]]. The pattern should therefore be reserved for tasks where the marginal gain in quality justifies this additional cost and time [[26]]. For simple tasks where a single-pass generation is sufficient, the overhead of setting up and running the loop is unnecessary and inefficient [[6]]. Strategic considerations for using this pattern include setting a maximum iteration limit to cap costs and using numeric scores instead of binary pass/fail judgments to allow for more flexible convergence thresholds [[27]].

DAG Orchestrators are generally optimized for performance and are highly effective at reducing end-to-end latency in workflows with parallelizable components. By default, a DAG execution engine will identify and run independent nodes concurrently, avoiding the serialization bottleneck of a linear chain [[15]]. Benchmarks for workflows with substantial parallelizable elements show end-to-end time reductions of 36-46% compared to their sequential counterparts [[15]]. This makes them ideal for tasks like aggregating data from multiple sources or generating multiple variants of an output simultaneously [[13]]. However, they face challenges with iterative logic. Implementing a loop within a traditionally acyclic graph requires special patterns, such as routing an edge back to a previous node, which can complicate the graph's structure and make it harder to reason about [[16]]. Over-parallelization is another pitfall; if too many small tasks are run in parallel, the scheduling overhead and contention for resources can outweigh the benefits of concurrency, leading to inefficiency [[15]]. Furthermore, while parallel execution speeds up the process, it also increases concurrent token consumption, which can be a significant cost factor [[17]]. The optimal use case for a DAG orchestrator is a well-defined pipeline where maximizing throughput by leveraging parallelism is the primary goal [[22]].

| **Cost Profile** | Variable. Cost is multiplied by the number of agent calls. Parallel execution can increase concurrent token usage [[12,17]]. | Highest. Reduces redundant computation but concurrent calls still multiply costs [[15,17]]. |

Less scalable for tasks requiring frequent, emergent changes to the workflow topology [[15]]. |

## Synthesis and Decision Framework for Web-Agent Design

The selection of an architectural pattern for a multi-agent web-agent system is not a matter of identifying a single "best" solution, but rather a strategic decision contingent on the specific requirements of the task at hand. State Graphs, Evaluator-Optimizer loops, and DAG Orchestrators represent three distinct points on a spectrum of control, flexibility, and efficiency. By synthesizing the comparative analysis of their control flow, coordination, state management, and performance characteristics, we can derive a practical decision framework to guide architectural choices for building effective and reliable web automation systems.

Choose the **State Graph** architecture, exemplified by LangGraph, when the primary drivers are the need for **maximum control, adaptability, and observability** in a complex, long-running, and stateful workflow. This pattern is ideal for mission-critical applications where the path of execution is not fully known in advance and may need to change dynamically based on intermediate results, user input, or environmental feedback [[10,12]]. Its explicit, code-defined structure provides unparalleled transparency, making it easier to debug, trace, and audit every step of the process [[32,34]]. The integrated support for human-in-the-loop review points, robust fault tolerance with retry policies and error handlers, and durable state persistence via checkpointers make it exceptionally well-suited for enterprise-grade production systems [[3,19,20]]. Ideal use cases include complex customer service automation requiring multi-step reasoning and approvals, financial transaction processing, or any workflow where the ability to pause, inspect, and resume from a specific point is non-negotiable [[12,34]]. The trade-off is increased complexity and potential performance overhead from checkpointing, which makes it less suitable for simple, linear tasks [[3,35]].

Opt for the **Evaluator-Optimizer loop** pattern when the highest priority is achieving **peak output quality and correctness**, and the task can be systematically improved through a dedicated cycle of generation and evaluation. This architecture is a specialized tool, not a general-purpose orchestrator. Its value proposition is the trade-off of increased cost and latency for superior results [[7,26]]. It excels in scenarios where clear, measurable evaluation criteria exist and LLM responses demonstrably improve when provided with specific, actionable feedback [[4,6]]. Common applications include autonomous code generation and debugging, where an evaluator can run test suites; content creation that must adhere to strict style guides or factual accuracy rubrics; and technical documentation generation that needs to validate against schemas or APIs [[6,40]]. The key advantage of this pattern is the separation of generator and evaluator, which mitigates confirmation bias and allows for more rigorous, objective assessment [[24]]. However, this comes with the responsibility of manually engineering robust termination conditions to prevent runaway loops and manage costs effectively [[27,28]]. It is ill-suited for tasks that are too simple for iteration or where evaluation criteria are purely subjective and inconsistent [[6,26]].

Select a **DAG Orchestrator** architecture when the workflow is **well-defined, repeatable, and benefits most from parallel execution** to maximize throughput and minimize latency. This pattern is inspired by traditional workflow engines and is best suited for business-critical pipelines where the execution path is known in advance and must be guaranteed [[12,22]]. Its strength lies in its ability to model parallelism naturally; independent tasks can be executed concurrently, dramatically reducing the end-to-end completion time for suitable workloads [[15]]. This makes it an excellent choice for data aggregation and synthesis tasks, such as pulling information from multiple web sources and combining it into a single report, or any pipeline composed of distinct, independent stages [[13]]. Many DAG orchestrators, like Microsoft's Conductor, offer a declarative, YAML-based syntax for defining workflows, which enhances clarity and maintainability [[16]]. The primary limitation is the acyclicity constraint, which complicates the modeling of iterative or cyclical logic and requires special patterns for loops [[16,30]]. Therefore, this architecture is best applied to structured, deterministic processes where the benefits of parallelism and guaranteed execution order outweigh the need for dynamic, emergent behavior.

In practice, these patterns are not mutually exclusive and are often combined in hybrid architectures to leverage their respective strengths. A common and powerful combination is a hierarchical supervisor agent (a State Graph pattern) that coordinates multiple parallel workers (a DAG fan-out/fan-in pattern) [[13,22]]. Another example is using a DAG to manage a series of independent data retrieval steps, followed by a final stage where the results are passed to an Evaluator-Optimizer loop for synthesis and refinement. Regardless of the chosen architecture, significant production engineering effort is required to address cross-cutting concerns such as cost monitoring, security guardrails, comprehensive observability, and effective context window management, as these are not fully solved by any single framework alone [[3,12,38]]. Ultimately, the decision should be guided by a clear understanding of the task's nature: use State Graphs for complex, adaptive reasoning; Evaluator-Optimizer loops for quality-focused refinement; and DAG Orchestrators for efficient, parallelizable pipelines.
